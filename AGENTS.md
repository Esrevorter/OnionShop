````markdown
# Project Blueprint: OnionMarket (Privacy-First Multi-Vendor Marketplace)

## 1. Project Overview
**Description:** A highly secure, privacy-first, multi-vendor e-commerce marketplace hosted as a Tor v3 Hidden Service (.onion). It features an internal escrow system, dispute resolution, and strict operational security.
**Core Philosophy:** Maximum security, zero JavaScript, server-side rendering, and strict trust-minimization.

---

## ⚠️ CRITICAL CONSTRAINTS FOR AI AGENT
1. **NO JAVASCRIPT:** The frontend must be 100% pure HTML5 and CSS3. Do not import, generate, or suggest any JavaScript, TypeScript, React, Vue, Alpine, or HTMX. All interactivity (forms, pagination, cart updates, dispute chats) must be handled via standard HTTP GET/POST requests and Server-Side Rendering (SSR).
2. **NO EXTERNAL FRONTEND DEPENDENCIES:** Do not use CDNs for CSS or fonts. All assets must be served locally from the Go binary or a local static directory.
3. **SECURITY FIRST:** Assume all user input is malicious. Use Go's native `html/template` (which auto-escapes XSS) instead of `text/template`. Never use `unsafe` packages.
4. **TOR CONTEXT:** The application will only be accessed via Tor. The web server will only see `127.0.0.1` as the client IP. **Do not use IP-based rate limiting.** Use Session-based or User-ID-based rate limiting.
5. **ESCROW ARCHITECTURE:** The platform acts as the escrow agent. BTCPay Server routes all funds to the **Platform's Master Wallet**. Vendors are credited via an internal ledger system, not direct on-chain payouts per order.

---

## 2. Technology Stack
*   **Language:** Go (Golang) 1.21+
*   **Web Framework:** `go-chi/chi` (Lightweight, idiomatic, standard `net/http` compatible).
*   **Templating:** Go standard library `html/template` (Strict SSR, auto-escaping).
*   **Database:** PostgreSQL 15+.
*   **Database Access:** `sqlc` (Generates type-safe, secure Go code from SQL queries) OR `jackc/pgx` (Direct, high-performance driver). *Avoid heavy ORMs like GORM to prevent SQL injection vectors and N+1 query issues.*
*   **Caching & Rate Limiting:** Redis (via `go-redis/redis`).
*   **Session Management:** `alexedwards/scs` (Secure, server-side sessions stored in Redis/Postgres).
*   **Payments:** BTCPay Server (REST API integration via standard `net/http` client).

```sql
-- Users & Roles
CREATE TABLE users (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    username VARCHAR(50) UNIQUE NOT NULL,
    password_hash VARCHAR(100) NOT NULL, -- Argon2id
    email VARCHAR(255) UNIQUE NOT NULL,
    role VARCHAR(20) NOT NULL DEFAULT 'customer', -- customer, vendor, moderator, admin
    pgp_public_key TEXT,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
);

-- Vendor Profiles
CREATE TABLE vendor_profiles (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID UNIQUE REFERENCES users(id) ON DELETE CASCADE,
    shop_name VARCHAR(100) UNIQUE NOT NULL,
    description TEXT,
    is_verified BOOLEAN DEFAULT FALSE,
    rating DECIMAL(3,2) DEFAULT 0.00
);

-- Catalog
CREATE TABLE categories (
    id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    slug VARCHAR(100) UNIQUE NOT NULL
);

CREATE TABLE products (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    vendor_id UUID REFERENCES vendor_profiles(id) ON DELETE CASCADE,
    category_id INT REFERENCES categories(id) ON DELETE SET NULL,
    title VARCHAR(200) NOT NULL,
    description TEXT NOT NULL,
    price_sats BIGINT NOT NULL, -- Store price in Satoshis to avoid float issues
    stock INT NOT NULL DEFAULT 0,
    is_active BOOLEAN DEFAULT TRUE,
    created_at TIMESTAMPTZ DEFAULT NOW()
);

-- Orders & Escrow
CREATE TABLE orders (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    customer_id UUID REFERENCES users(id) ON DELETE PROTECT,
    vendor_id UUID REFERENCES vendor_profiles(id) ON DELETE PROTECT,
    status VARCHAR(20) NOT NULL DEFAULT 'pending', -- pending, paid, shipped, completed, disputed, cancelled
    escrow_status VARCHAR(20) NOT NULL DEFAULT 'awaiting_payment', -- awaiting_payment, in_escrow, released, refunded, disputed
    total_sats BIGINT NOT NULL,
    btcpay_invoice_id VARCHAR(100) UNIQUE,
    encrypted_shipping_info TEXT, -- PGP encrypted
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE order_items (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    order_id UUID REFERENCES orders(id) ON DELETE CASCADE,
    product_id UUID REFERENCES products(id) ON DELETE PROTECT,
    quantity INT NOT NULL,
    price_sats BIGINT NOT NULL -- Price at the moment of purchase
);

-- Vendor Internal Ledger (Tracks platform credits, not direct BTC)
CREATE TABLE vendor_ledger (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    vendor_id UUID REFERENCES vendor_profiles(id) ON DELETE CASCADE,
    order_id UUID REFERENCES orders(id) ON DELETE SET NULL, -- Null for manual adjustments/withdrawals
    amount_sats BIGINT NOT NULL, -- Positive for credits, negative for debits
    type VARCHAR(30) NOT NULL, -- 'escrow_credit', 'withdrawal', 'dispute_refund', 'admin_adjustment'
    description TEXT,
    created_at TIMESTAMPTZ DEFAULT NOW()
);

-- Vendor Withdrawal Requests
CREATE TABLE vendor_withdrawals (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    vendor_id UUID REFERENCES vendor_profiles(id) ON DELETE CASCADE,
    amount_sats BIGINT NOT NULL,
    btc_address TEXT NOT NULL, -- Destination address for the payout
    status VARCHAR(20) NOT NULL DEFAULT 'pending', -- 'pending', 'processing', 'completed', 'failed'
    txid VARCHAR(100), -- On-chain transaction ID once processed
    created_at TIMESTAMPTZ DEFAULT NOW(),
    processed_at TIMESTAMPTZ
);

-- Dispute System
CREATE TABLE disputes (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    order_id UUID UNIQUE REFERENCES orders(id) ON DELETE CASCADE,
    opened_by UUID REFERENCES users(id) ON DELETE CASCADE, -- Customer or Vendor
    reason TEXT NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'open', -- 'open', 'moderator_review', 'resolved'
    resolution TEXT, -- Moderator's notes
    resolved_by UUID REFERENCES users(id),
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
);

-- Dispute Messages (Chat between Customer, Vendor, and Mod)
CREATE TABLE dispute_messages (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    dispute_id UUID REFERENCES disputes(id) ON DELETE CASCADE,
    user_id UUID REFERENCES users(id) ON DELETE CASCADE,
    message TEXT NOT NULL,
    is_moderator BOOLEAN DEFAULT FALSE,
    created_at TIMESTAMPTZ DEFAULT NOW()
);

## 5. Core Business Logic & Workflows

### A. Role-Based Access Control (RBAC)
*   Implement a middleware in `internal/middleware/auth.go`.
*   Roles: `customer`, `vendor`, `moderator`, `admin`.
*   Middleware should check the user's role from the session context before allowing access to specific route groups.

### B. Anti-DDoS & Tor Optimization
*   **Context:** All requests originate from `127.0.0.1` via the Tor daemon. IP blocking is impossible.
*   **Rate Limiting:** Implement a sliding-window rate limiter using Redis in `internal/middleware/ratelimit.go`. 
    *   Limit by `session_id` for unauthenticated users.
    *   Limit by `user_id` for authenticated users.
    *   Strict limits on `POST /login`, `POST /register`, and `POST /checkout`.
*   **Bot Mitigation (No-JS):**
    *   **Honeypot:** Add a hidden CSS field (`display: none`) to forms. If populated on POST, reject.
    *   **Math CAPTCHA:** For registration and checkout (e.g., "What is 12 + 4?"). Store the hashed answer in the server-side session.

### C. BTCPay Server Integration (Platform Wallet)
*   Create a service in `internal/services/btcpay.go`.
*   **Configuration:** BTCPay must be configured as a *single storefront*. All funds settle into the Platform's Master Wallet. Do not use automatic payouts to individual vendor wallets.
*   **Flow:** 
    1. Calculate cart total in Satoshis.
    2. Call BTCPay API to create an invoice.
    3. Render the QR code (using `github.com/skip2/go-qrcode`) and payment URL.
    4. Create a webhook handler (`POST /api/webhooks/btcpay`) to listen for payment confirmations. **Crucial:** Verify the `BTCPay-Sig` header to prevent spoofed events.

### D. Escrow & Dispute State Machine
*   Implement logic in `internal/services/escrow.go` and `internal/services/ledger.go`.
*   **The Happy Path:**
    1. Customer pays -> `Order.escrow_status` = `in_escrow`.
    2. Vendor ships -> `Order.status` = `shipped`.
    3. Customer confirms receipt -> `Order.escrow_status` = `released`.
    4. **Action:** `ledger_service.CreditVendor()` adds the `total_sats` to the vendor's `vendor_ledger` balance as an `escrow_credit`.
*   **The Dispute Path:**
    1. Customer opens dispute -> `Order.escrow_status` = `disputed`.
    2. Moderator reviews `dispute_messages`.
    3. Mod resolves in favor of Vendor -> Funds credited to `vendor_ledger`.
    4. Mod resolves in favor of Customer -> Platform refunds customer from operational hot wallet (since on-chain funds are already in the platform wallet). Order marked `refunded`.
*   **Auto-Finalization:** Implement a background worker (e.g., `go-co-op/gocron`) to auto-release escrow if the customer doesn't confirm within 14 days of the `shipped` timestamp.

### E. Security Headers & CSRF
*   Implement a middleware to set strict HTTP headers:
    *   `Content-Security-Policy: default-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:;` (Strict CSP, no JS).
    *   `X-Content-Type-Options: nosniff`
    *   `Referrer-Policy: no-referrer`
*   **CSRF Protection:** Use `github.com/justinas/nosurf` or implement a custom CSRF token generator. Every `POST`, `PUT`, `DELETE` form must include a hidden CSRF token validated against the session.
````
