## ADR-001 — TLS identity: self-signed exact-onion-SAN, no pinning
**Date:** 2026-11-24 · **Status:** accepted, implemented

**Decision.** No SPKI/certificate-hash pinning, no HPKP, no publicly CA-issued
certificates, no HSTS. The storefront presents a **self-signed ECDSA P-384** leaf
whose DNS SAN is exactly the service's v3 `.onion` hostname, generated by
`scripts/gen-certs.sh <hostname>.onion`.

**Rationale.** The Tor onion protocol already authenticates the endpoint: the
service descriptor is signed by the onion identity key and published in the
consensus. A CA adds a third party that can be compelled or compromised, and
pins are brittle — a rotated TLS key bricks every client that pinned it, with no
recovery path short of training users to ignore warnings. Both are worse than
the property we actually need.

**Consequences.**
- The TLS key is separate and random; it is *not* the Tor Ed25519 key and is not
  cryptographically bound to it. SAN match validates hostname, not trust.
- Never publish a pin, never advise bypassing a browser warning, never import an
  unverified trust root. If the supported Tor Browser warns, stop deployment.
- Verification is behavioural: clean Tor Browser profile, exact supported build.

## ADR-002 — Settlement: in-house monero-wallet-rpc client
**Date:** 2026-11-24 · **Status:** accepted, implemented

**Decision.** Neither **BTCPay Server** nor **MoneroPay** is used. Settlement is a
direct JSON-RPC client against our own `monerod` + `monero-wallet-rpc`:
`create_address` per order, `get_transfers` for observation, confirmation and
amount gating in our own escrow state machine.

**Rationale.**
- *Bitcoin* has no retroactive privacy: every deposit, payout and refund is a
  permanent public graph edge, deanonymising operator and buyers years later.
  Tor and LUKS cannot fix that. Monero removes the public graph.
- *BTCPay* additionally brings clearnet correlation surfaces (rate providers,
  release checks, plugin builder, explorer links) onto the same host as the
  market, plus a hot-wallet incident history that makes it a poor custody
  neighbour. Its placeholder service in this repo could never have detected a
  payment: no `bitcoind`, no NBXplorer, a fake image digest, and an egress hole.
- *MoneroPay* is essentially the client we needed, already written — but it adds
  a daemon, a second database, and an HTTP API with **no authentication** that
  exposes spend alongside receive. Reachability equals spend authority. Writing
  the ~500-line client ourselves removes that entire surface.

**Consequences.**
- **Polling only, never webhooks.** The hidden service is unreachable inbound; a
  callback URL would be an egress/correlation artifact.
- `monero-wallet-rpc` is internal-only with **no published ports** (Docker
  publishes ahead of host firewall rules).
- One subaddress per order, never rebound. Confirmation requires the order's own
  subaddress **and** the exact amount **and** the confirmation threshold.
  Overpayment flags for manual review and never auto-releases; underpayment
  records the delta.
- Money is integer cents/piconero end to end; decimal input parsed exactly.
- Mainnet still requires the airgapped **view-only** ceremony. The dev testnet
  wallet is not a custody model.
